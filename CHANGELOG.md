## Release Notes Best Practices

### Recommended Workflow for Future Releases

1. **Before each release:**
   - Update the `[Unreleased]` section with all changes since the last release
   - Categorize changes under: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`

2. **During release:**
   - Move `[Unreleased]` content to a new version section
   - Add the release date in format `YYYY-MM-DD`
   - Update version in `package.json`
   - Commit CHANGELOG.md together with version bump

3. **Automation options:**
   - Use `standard-version` or `semantic-release` npm packages
   - Configure GitHub Actions to auto-generate release notes
   - Use conventional commits for automatic changelog generation

### Conventional Commits Format (Recommended)

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

Types:
- `feat`: New feature (maps to Added)
- `fix`: Bug fix (maps to Fixed)
- `docs`: Documentation changes
- `style`: Code style changes
- `refactor`: Code refactoring (maps to Changed)
- `perf`: Performance improvements
- `test`: Test additions/changes
- `chore`: Maintenance tasks

Example:
```
feat(product): add external category IDs support

AVANTAN8N-25
```
